# Audit: Flux and Kubernetes manifests

Review of every YAML file in this repository (the Flux entry point, the three app bases and the
templates) as of September 2026. It covers security, setup errors and outdated settings.
`cluster/me/flux-system/gotk-components.yaml` is generated by Flux and was not reviewed
line by line.

> **Later changes.** After this audit the Flux directory became `cluster/me`, the repository
> `project-me-config`, and the Kustomizations `project-me-<svc>-sync-prod`. Findings 1–19 quote
> files as they were at audit time. Findings E1–E9 ([Config sync](#config-sync-2026-09-28)) cover
> the naming and ConfigMap sync that followed.

**Severity:** Blocker = Flux can't reconcile · High = security or availability risk · Medium =
likely to cause a failed or confusing deploy · Low = hardening or hygiene · Info = worth knowing.

**Status:** Fixed · Partially fixed · Documented (handled by a manual step) · Recommended (not changed).

## Findings

### 1. GitRepository SSH URL is malformed — Blocker, Fixed

`cluster/my-apps/flux-system/gotk-sync.yaml:14` had `ssh://git@github.com:hungnh1812dev/...`.
With the `ssh://` scheme, a `:` after the host means a port number, so source-controller couldn't
clone the repository and nothing downstream would reconcile.

**Fix:** `ssh://git@github.com/hungnh1812dev/my-apps-config.git` (commit `61889e7`).

### 2. Root Kustomization path is wrong — Blocker, Fixed

`gotk-sync.yaml:23` had `path: ./clusters/my-apps`, but the directory is `cluster/my-apps`.
The `flux-system` Kustomization would fail with "path not found", so none of the app syncs would
be created.

**Fix:** `path: ./cluster/my-apps` (commit `61889e7`; the directory is now `cluster/me`). This file
is generated by Flux, so always bootstrap with `--path=cluster/me` (see [DEPLOYMENT.md](DEPLOYMENT.md))
or it will be regenerated with a different path.

### 3. frontend sync path doesn't exist — Blocker, Fixed

`cluster/my-apps/frontend-sync.yaml:21` had `path: ./apps/frontend/k8s/flux`, a layout from the
app repository this was copied from.

**Fix:** `path: ./apps/frontend` (commit `61889e7`).

### 4. Pods run without a security context — High, Partially fixed

None of the three Deployments set a `securityContext`, and all mounted a service-account token
they never use. A compromised container could escalate privileges, use every default Linux
capability, and call the Kubernetes API with the pod's token.

**Fixed for all three** (commits `30887db`, `dbd4289`, `36ed2ed`):

| Setting | cms-api | cms-admin | frontend |
|---|---|---|---|
| `automountServiceAccountToken: false` | ✓ | ✓ | ✓ |
| `seccompProfile: RuntimeDefault` | ✓ | ✓ | ✓ |
| `allowPrivilegeEscalation: false` | ✓ (both containers) | ✓ | ✓ |
| `capabilities.drop: [ALL]` | ✓ (both containers) | ✓, adds back `NET_BIND_SERVICE`, `CHOWN`, `SETUID`, `SETGID` | ✓ |
| `runAsNonRoot: true` | — | — | — |

**Still open:** `runAsNonRoot`. The images are built in the app repository, and whether they
set a non-root `USER` can't be checked from here. If an image runs as root, `runAsNonRoot: true`
stops the pod from starting (`CreateContainerConfigError`). Next steps:

- cms-api and frontend: check the Dockerfiles. If they set a non-root `USER`, add
  `runAsNonRoot: true` to the pod `securityContext`.
- cms-admin: stock nginx has to start as root to bind port 80. Switch the image to
  `nginxinc/nginx-unprivileged` (it listens on 8080), update `containerPort` and the Service
  `targetPort`, then add `runAsNonRoot: true` and remove the added capabilities.
- `readOnlyRootFilesystem` was left out on purpose: nginx, Next.js and Prisma all write to disk,
  and each would need `emptyDir` mounts.

**Runtime risk:** the cms-admin capability set wasn't tested against the real image. If the pod
crash-loops with a `chown` or `setgid` permission error, remove the `capabilities` block from
`apps/cms-admin/deployment.yaml:33`.

### 5. Filled-in templates could be committed — High, Fixed

The templates say to `cp` each one to a sibling file and fill in real values, but the repo had
no `.gitignore`. One `git add .` would have pushed database passwords and JWT secrets to GitHub.

**Fix:** `.gitignore` ignores `templates/*.yaml` except `*.example.yaml` (commit `3bee4f2`).

### 6. Comments describe another repository — Medium, Fixed

Comments across `apps/`, `cluster/` and `templates/` referred to `clusters/abyssdev/...`,
`k8s/flux`, `abyssdev-*` Kustomization names, a `deployment` branch, `master`, and CI "bump-tag"
jobs. None of these exist here. Flux reads `main`, and image tags are committed by the app
repository. Following those comments during an incident would send you to the wrong place.

**Fix:** all rewritten to match this repository (commits `30887db`, `dbd4289`, `36ed2ed`, `3bee4f2`).

### 7. ConfigMap template names didn't match — Medium, Fixed

Each ConfigMap template had `name: <app-name>-<app-service-name>-<app-env>-config`, but each sync
file reads a fixed name (`my-apps-<svc>-prod-config`). A ConfigMap named after the template
pattern would never be found, and every `${APP_*}` would come out empty.

**Fix:** the templates were changed to the exact names (commit `3bee4f2`). **Superseded by E6:** the
templates are back to placeholder names, which the docs say to fill in so they become the exact
names in the sync files.

### 8. The app namespace isn't created by Flux — Medium, Documented

All three apps deploy into `<APP_NAMESPACE>-<APP_ENV>`, but no manifest creates it, so the first
reconcile fails until it exists. Adding a Namespace to one app's base would be worse: that app's
Kustomization has `prune: true`, so removing the app would delete the namespace and the other two
apps with it.

**Handling:** created by hand once, before the Secrets ([DEPLOYMENT.md](DEPLOYMENT.md), step 6).

### 9. Placeholder image tag `dev` — Medium, Recommended

`cms-admin-sync.yaml` and `frontend-sync.yaml` have `APP_IMAGE_TAG: "dev"`. Unless the image
repository really has a `dev` tag, the first deploy ends in `ImagePullBackOff`. With `wait: true`,
that Kustomization then reports not Ready until the app repository commits a real tag.

**Recommendation:** have the app repository commit a real tag for each service before bootstrap,
or expect those two Kustomizations to stay not Ready until it does.

### 10. cms-api init container has no resources — Medium, Fixed

The `prisma migrate deploy` init container had no requests or limits, so it could be scheduled on
a node without room for it, or use unbounded memory.

**Fix:** requests `50m`/`128Mi`, limits `500m`/`512Mi` (`apps/cms-api/deployment.yaml:40`, commit `30887db`).

### 11. No `retryInterval` — Low, Fixed

A failed apply waited for the next full `interval` (3m) before retrying.

**Fix:** `retryInterval: 1m` on all three sync files (commits `30887db`, `dbd4289`, `36ed2ed`).

### 12. frontend has no `dependsOn` — Low, Recommended against

It was considered and rejected. The frontend's probes are designed to tolerate cms-api being down:
liveness is only a TCP check, and `/api/health` always returns 200. A `dependsOn` would block
every frontend deploy while cms-api's Kustomization is not Ready, for example after a bad cms-api
tag. The reasoning is recorded in a comment in `cluster/me/frontend-sync.yaml`.

### 13. No image pull secret — Low, Documented

The Deployments don't set `imagePullSecrets`. That's correct for public GHCR packages, but
private ones would fail with `ImagePullBackOff`.

**Handling:** an optional step in [DEPLOYMENT.md](DEPLOYMENT.md) creates the secret and attaches
it to the namespace's default service account, so no manifest has to change.

### 14. No NetworkPolicy — Low, Recommended

Any pod in the cluster can reach cms-api directly, bypassing Traefik and its HTTPS redirect.

**Recommendation:** add a default-deny ingress policy in the app namespace. Allow Traefik (in
`kube-system` on k3s) to reach all three services, and allow frontend to reach cms-api. k3s
enforces NetworkPolicy by default.

### 15. Single replica, no PodDisruptionBudget — Low, Recommended

Every Deployment has `replicas: 1`, so each rollout and node drain causes a short outage.
On a single-node cluster this is usually acceptable.

**Recommendation:** if downtime matters, use `replicas: 2` for frontend and cms-admin, and add a
PDB. cms-api needs care first: two pods running `prisma migrate deploy` at once rely on Prisma's
migration lock.

### 16. No HSTS or security headers — Low, Recommended

The Middleware only redirects HTTP to HTTPS. Browsers aren't told to stay on HTTPS (HSTS), and no
`X-Content-Type-Options` or `Referrer-Policy` headers are added.

**Recommendation:** add a Traefik `headers` Middleware (`stsSeconds`, `stsIncludeSubdomains`,
`contentTypeNosniff`, `referrerPolicy`) and chain it in each Ingress's `router.middlewares` annotation.

### 17. Secrets applied by hand — Low, Recommended

Secrets live only on the cluster, so rebuilding the cluster means recreating them from wherever
you keep the values. Keeping them out of git was a deliberate choice for now.

**Recommendation (later):** SOPS with an age key, decrypted by Flux's kustomize-controller, keeps
encrypted Secrets in this repository and makes the cluster fully rebuildable from git.

### 18. Mutable, architecture-specific tags — Info, Recommended

Tags like `81-47e63ce-amd64` can be overwritten in the registry, and the `-amd64` suffix means the
node must be amd64.

**Recommendation:** keep the commit SHA in the tag (as now) and never push to an existing tag.
Pinning by digest (`@sha256:...`) is stricter but makes the app repository's tag rewrite more complex.

### 19. Flux version — Info, Recommended

`gotk-components.yaml:3` pins Flux v2.9.5. The Flux release in use wasn't checked against the
latest while writing this audit.

**Recommendation:** run `flux check` after bootstrap, and upgrade with the steps in
[DEPLOYMENT.md](DEPLOYMENT.md) (Upgrading Flux) when a newer release is out.

## Config sync (2026-09-28)

A second pass after the three apps' configuration drifted apart.
All YAML parsed and rendered with `kubectl kustomize`, but after Flux substitutes the `${APP_*}`
variables several names one resource uses to point at another didn't match. Resources are named
`<APP_SERVICE_NAME>-<APP_ENV>`, while many references still used
`<APP_NAME>-<APP_SERVICE_NAME>-<APP_ENV>`. The fix keeps `metadata.name` and changes every
reference to match it. Labels and selectors are unchanged.

At the same time the config was split: a shared ConfigMap (`project-me-prod-shared-config`:
`APP_NAME`, `APP_NAMESPACE`, `APP_ENV`, `APP_DOMAIN`, `APP_TLS_CLUSTER_ISSUER`) plus one per app
(`project-me-<svc>-prod-config`: `APP_SERVICE_NAME`, `APP_IMAGE_REPO`, `APP_PORT`). Each sync file
reads the shared one first and its own second. See [configuration.md](components/configuration.md).

### E1. Ingress backend points at a missing Service — Blocker, Fixed

`apps/*/ingress.yaml` sent traffic to `${APP_NAME}-${APP_SERVICE_NAME}-${APP_ENV}`, but the Service
is `${APP_SERVICE_NAME}-${APP_ENV}`. Every host would have returned 404/503 from Traefik.
**Fix:** backend and TLS `secretName` use `${APP_SERVICE_NAME}-${APP_ENV}` (all three apps).

### E2. Middleware annotation doesn't match — Blocker, Fixed

The annotation referenced `<ns>-${APP_NAME}-${APP_SERVICE_NAME}-${APP_ENV}-https-redirect`, but the
Middleware is `${APP_SERVICE_NAME}-${APP_ENV}-https-redirect`. Traefik rejects a router whose
middleware doesn't exist, so the host would not be served at all.
**Fix:** `${APP_NAMESPACE}-${APP_ENV}-${APP_SERVICE_NAME}-${APP_ENV}-https-redirect@kubernetescrd`.

### E3. Secret reference doesn't match the template — Blocker, Fixed

The cms-api (both containers) and frontend Deployments loaded `${APP_NAME}-…-secrets`, while the
Secret templates create `<app-service-name>-<app-env>-secrets`. Pods would stay in
`CreateContainerConfigError`. **Fix:** `envFrom` uses `${APP_SERVICE_NAME}-${APP_ENV}-secrets`, and
the templates' comments state the required name.

### E4. Missing `ingress` Component — Blocker, Fixed

`cluster/me/cms-api-sync.yaml` had `components: [ingress]`, but the Ingress and Middleware had
moved into `apps/cms-api` itself and `apps/cms-api/ingress/` no longer existed, so the Flux build
failed. **Fix:** `components:` removed. cms-api has the same layout as the other two apps.

### E5. frontend `APP_PORT` undefined — Blocker, Fixed

The frontend Deployment and Service use `${APP_PORT}`, but its ConfigMap template had no such key,
so `containerPort` and `port` rendered empty and the API server would reject them.
**Fix:** `APP_PORT` added to `templates/frontend-configmap.example.yaml`. It must equal the image's
`PORT` (3000).

### E6. ConfigMap names disagree — High, Fixed

The sync files read `project-me-<svc>-sync-prod-config`, the templates were named
`<app-name>-<svc>-<env>-config`, and comments said `my-apps-<svc>-prod-config`.
**Fix:** the sync files read `project-me-prod-shared-config` and `project-me-<svc>-prod-config`. The
templates keep placeholder names that become those names when filled in, and DEPLOYMENT.md step 7
checks them with `kubectl get`.

### E7. Stale `my-apps` references — Medium, Fixed

Comments in `apps/`, `cluster/me/`, `templates/`, the component docs, DEPLOYMENT.md and README still
said `cluster/my-apps`, `my-apps-config` and `my-apps-*`. **Fix:** updated to `cluster/me`,
`project-me-config` and `project-me-*`. Quotes in findings 1–19 are kept as they were.

### E8. `APP_PORT` in the cms-api Secret — Low, Fixed

The Secret template set `APP_PORT`, which only Flux reads (from the ConfigMap), while its own comment
said not to set it. **Fix:** removed.

### E9. Wrong frontend port comments — Low, Fixed

The frontend Service comment said "port 3000", and the Deployment said "PORT=${APP_PORT} is set in
the image". **Fix:** both now say the image sets `PORT`, and `APP_PORT` must equal it.

### Verification (config sync)

- `kubectl kustomize` renders all three apps and `cluster/me`.
- A render substituted with only the keys defined in the shared and per-app templates (plus
  `APP_IMAGE_TAG`) was checked for each app: Ingress backend = Service name, middleware annotation =
  Middleware `<namespace>-<name>`, `envFrom` Secret = the Secret template's name, ports are ints.
- The three sync files differ only in name, path, per-app ConfigMap and tag.

**Not verified:** `flux build` and `kubeconform` (not installed). `envsubst` doesn't implement Flux's
`${VAR:=default}`, so the frontend Ingress host was checked by reading it.

## Verification done

- `kubectl kustomize` renders `apps/cms-api`, `apps/cms-api/ingress`, `apps/cms-admin`,
  `apps/frontend` and `cluster/my-apps`.
- Diffs of the `apps/` and `cluster/` changes only add fields or change comments. No names,

- No stale references remain in `apps/`, `cluster/` or `templates/`.

**Not verified:** Flux variable substitution (`flux build`) and schema validation (`kubeconform`)
